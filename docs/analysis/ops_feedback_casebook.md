# 샘플 기반 현업 피드백 대응표

## 목적

실제 STT 성격의 상담 예시를 기준으로, 어떤 현업 피드백이 예상되는지와 어떤 규칙으로 선제 대응할지를 연결한다.
이 문서는 프롬프트 문구를 늘리기보다 `feedback_rules`, `analysis_hints`, `self-check`를 어떻게 조정해야 하는지 빠르게 판단하는 데 목적이 있다.

## 샘플 케이스

### 케이스 1. 보험금 청구 진행 상태 문의

원문 성격:

- 고객이 지난주 서류 제출 후 결과를 아직 받지 못했다고 문의한다.
- 배우자 계약인지 본인 계약인지 관계 정보가 중요하다.
- 이전 안내가 불명확했다고 불만을 제기한다.

예상 현업 피드백:

1. 고객 요청 사항이 첫 줄에 안 보인다.
2. 처리 상태가 빠졌다.
3. 계약자/피보험자 관계가 빠졌다.
4. 이전 안내에 대한 불만이 약하게 표현됐다.
5. 상담사 후속조치가 있으면 반드시 보여야 한다.

선제 대응 규칙:

- `feedback_rules.must_include`: `처리 상태`, `계약자/피보험자 관계`, `불만 사유`, `상담사 후속조치`
- `feedback_rules.priority_topics`: `고객 요청 사항`, `민원/불만`, `처리 상태`
- `analysis_hints.missing_points`: `상담 목적`, `처리 상태`, `관계 정보`, `후속조치`
- `self-check`: 고객 요청과 처리 상태가 분리되어 보이는지 확인

좋은 요약 방향:

- 첫 줄에 `보험금 청구 결과 확인 요청`을 둔다.
- `배우자 계약 관련 문의`처럼 관계 정보를 별도 항목으로 둔다.
- `이전 안내 불명확`을 민원/불만 항목으로 분리한다.
- 상담사 안내가 있으면 처리 상태와 별도 항목으로 적는다.

### 케이스 2. 계약 변경 또는 자동이체 변경 문의

원문 성격:

- 고객이 자동이체 계좌 변경 방법을 묻는다.
- 본인 명의 계좌 여부, 변경 가능 시점, 필요 서류가 핵심이다.
- 상담사는 절차와 제한 조건을 안내한다.

예상 현업 피드백:

1. 고객 요청보다 절차 설명이 먼저 나온다.
2. 필요 조건이 빠졌다.
3. 상담사 후속 안내가 누락됐다.
4. 결과가 아니라 단순 설명만 길다.

선제 대응 규칙:

- `feedback_rules.must_include`: `고객 요청 사항`, `상담사 후속조치`, `고객이 기대하는 결과`
- `feedback_rules.must_avoid`: `장황한 배경 설명`
- `feedback_rules.negative_patterns`: `배경 설명이 고객 요청보다 먼저 나오는 요약`
- `analysis_hints.suggested_focus`: `고객 요청 사항을 첫 줄에 배치`, `후속조치를 분리해서 요약`

좋은 요약 방향:

- `자동이체 계좌 변경 요청`을 먼저 적는다.
- `본인 명의 계좌 필요` 같은 제한 조건은 핵심 상황으로 짧게 적는다.
- `변경 방법 안내` 또는 `추가 서류 제출 안내`를 후속조치로 분리한다.

### 케이스 3. 민원 또는 불만 중심 상담

원문 성격:

- 고객이 이전 처리 지연, 안내 오류, 콜백 미이행 등을 문제 삼는다.
- 고객의 요구는 단순 문의가 아니라 개선 요청 또는 즉시 확인 요청이다.

예상 현업 피드백:

1. 민원 강도가 약하게 표현됐다.
2. 고객 요구가 아닌 배경 설명 위주로 요약됐다.
3. 처리 상태와 향후 조치가 안 보인다.
4. 감정 해석이 과장되거나 반대로 지나치게 완화됐다.

선제 대응 규칙:

- `feedback_rules.must_include`: `불만 사유`, `처리 상태`, `상담사 후속조치`
- `feedback_rules.must_avoid`: `불필요한 감정 해석`
- `analysis_hints.quality_issues`: `고객 요청보다 배경 설명이 앞서는 문제`
- `self-check`: 민원/불만이 특이사항으로 밀리지 않았는지 확인

좋은 요약 방향:

- `처리 지연에 대한 확인 및 개선 요청`처럼 고객 요구를 먼저 쓴다.
- `이전 안내 불일치` 또는 `콜백 미이행 불만`을 민원/불만 항목에 직접 적는다.
- `재확인 후 콜백 예정` 같은 후속조치를 별도 항목으로 유지한다.

### 케이스 4. 개인정보와 비핵심 세부값이 많은 상담

원문 성격:

- STT에 이름, 생년월일, 상세 주소, 계좌번호 일부, 상세 시각, 세부 금액이 많이 포함된다.
- 실제 업무상 필요한 것은 요청 목적, 상태, 기한, 결과 정도다.

예상 현업 피드백:

1. 개인정보가 너무 많이 남았다.
2. 핵심과 무관한 숫자 정보가 과다하다.
3. 읽기 어렵고 검수 포인트가 흐려진다.

선제 대응 규칙:

- `feedback_rules.must_avoid`: 개인정보, 비핵심 세부 금액과 상세 시각
- `analysis_hints.over_summary_points`: 개인정보 과다 포함, 세부 금액/날짜 포함
- `self-check`: 제거 대상 정보가 남지 않았는지 확인

좋은 요약 방향:

- 업무 판단에 필요한 날짜, 금액만 최소한으로 남긴다.
- 식별 가능한 개인정보는 제거하거나 마스킹한다.
- 숫자 정보는 `청구 금액 관련 문의`, `지난주 접수`처럼 실무 수준으로 축약한다.

### 케이스 5. 다른 맥락의 STT 혼입 가능성이 있는 상담

원문 성격:

- 현재 문의와 직접 관련 없는 대화 조각이나 이전 통화 맥락이 섞여 있다.
- 상태나 주체가 중간에 바뀌는 문장이 존재한다.

예상 현업 피드백:

1. 현재 상담과 무관한 내용이 들어갔다.
2. 주체가 혼동된다.
3. 완료/진행 상태를 잘못 썼다.

선제 대응 규칙:

- `analysis_hints.quality_issues`: 다른 맥락의 STT 혼입 가능성 미점검
- `feedback_rules.negative_patterns`: 원문에 없는 처리 결과를 추정해서 쓰는 요약
- `self-check`: 다른 맥락으로 보이는 문장을 보수적으로 제외했는지 확인

좋은 요약 방향:

- 현재 상담 목적과 직접 연결되지 않는 문장은 제외한다.
- 상태 표현은 확실한 문장만 근거로 사용한다.
- 계약자, 피보험자, 상담사 주체가 바뀌는 부분은 보수적으로 정리한다.

## 운영 팁

1. 현업 피드백이 들어오면 먼저 이 다섯 케이스 중 어디와 가장 유사한지 매핑한다.
2. 프롬프트 본문 수정 전 `feedback_rules` 또는 `analysis_hints` 보강으로 해결 가능한지 먼저 본다.
3. 같은 피드백이 3회 이상 반복되면 기본 예시 JSON에 승격한다.
4. 실제 검수 코멘트는 `누락`, `과다`, `순서`, `용어`, `근거성` 태그와 함께 축적한다.
