# 입력 데이터 구조안

## 목적

요약 품질 문제를 프롬프트 문장만으로 해결하지 않기 위해,
입력 데이터를 역할별로 분리한다.

## 권장 상위 구조

```json
{
  "source": {},
  "task_config": {},
  "feedback_rules": {},
  "analysis_hints": {}
}
```

## 1. `source`

원문과 메타정보를 담는다.

```json
{
  "source_text": "상담 원문",
  "channel": "call_center",
  "consult_type": "보험금청구",
  "speaker_map": {
    "A": "고객",
    "B": "상담사"
  }
}
```

역할:

- 모델이 직접 근거로 삼는 본문
- 상담 유형 분류의 기준
- 화자 관계 해석의 기준

## 2. `task_config`

이번 실행의 목표와 출력 형식을 담는다.

```json
{
  "summary_goal": "고객 관점 핵심 요약",
  "output_format": "bullet",
  "required_sections": [
    "고객 요청 사항",
    "계약/대상 관계",
    "처리 상태",
    "민원/불만"
  ],
  "max_items": 7
}
```

역할:

- 출력 구조를 고정한다.
- 모델이 어디까지 요약할지 범위를 제한한다.

## 3. `feedback_rules`

현업 피드백에서 정책화된 항목만 담는다.

```json
{
  "must_include": [
    "계약자/피보험자 관계",
    "처리 지연 여부",
    "불만 사유"
  ],
  "must_avoid": [
    "상담사 인사말",
    "반복된 공감 표현"
  ],
  "preferred_labels": {
    "문의 목적": "고객 요청 사항",
    "진행 상태": "처리 상태"
  },
  "priority_topics": [
    "고객 요청 사항",
    "민원/불만",
    "처리 상태"
  ]
}
```

역할:

- 단건 코멘트가 아니라 누적 운영 룰만 반영한다.
- 현업 화면, QA 기준, 보고서 문구와 용어를 맞춘다.

## 4. `analysis_hints`

LLM judge 또는 이전 실험에서 얻은 개선 포인트를 담는다.

```json
{
  "missing_points": [
    "문의 목적 누락",
    "처리 지연 불만 누락"
  ],
  "over_summary_points": [
    "배경 설명 과다"
  ],
  "quality_issues": [
    "핵심 정보가 뒤에 배치됨"
  ],
  "suggested_focus": [
    "고객 요청과 불만을 먼저 요약"
  ]
}
```

역할:

- 현재 프롬프트의 약점을 보완한다.
- 다음 출력에서 우선 점검할 포인트를 준다.
- 사실 근거가 아니라 개선 힌트로만 사용한다.

## 권장 운영 규칙

1. `source`는 항상 필수다.
2. `task_config`는 상담 유형별 기본 템플릿을 둔다.
3. `feedback_rules`에는 검증된 누적 규칙만 넣는다.
4. `analysis_hints`는 최신 평가 결과를 반영하되, 원문보다 우선하지 않는다.

## 좋지 않은 구조

아래처럼 한 필드에 모든 것을 섞지 않는다.

```json
{
  "context": "원문, 피드백, 주의사항, 예외, 선호 표현, 지난 평가 결과를 한 문단으로 합친 텍스트"
}
```

이 구조는 모델이 사실, 규칙, 힌트를 구분하지 못하게 만든다.
