# 프롬프트 설계 원칙서

## 목적

이 문서는 상담 요약 프롬프트를 계속 덧붙이다가 발생하는 한계를 피하기 위해,
프롬프트 자체보다 먼저 고정해야 할 설계 원칙을 정의한다.

핵심 목표는 다음 4가지다.

1. 원문 근거성을 유지한다.
2. 현업이 원하는 요약 포인트를 안정적으로 반영한다.
3. 모델이나 버전이 바뀌어도 출력 품질이 크게 흔들리지 않게 한다.
4. 프롬프트만으로 해결할 수 없는 문제를 구조로 분리한다.

## 먼저 인정해야 할 프롬프트 한계

프롬프트를 길게 쓰면 다음 문제가 반복된다.

1. 규칙이 많아질수록 모델이 일부 규칙만 선택적으로 따른다.
2. 우선순위가 불명확하면 같은 입력에도 출력이 흔들린다.
3. 현업 피드백이 누적될수록 예외 규칙이 비대해진다.
4. 모델 교체 시 같은 프롬프트라도 해석 방식이 달라진다.
5. 누락, 과잉 요약, 표현 선호, 정책 준수를 한 문서에서 동시에 제어하기 어렵다.

따라서 프롬프트는 모든 문제를 해결하는 수단이 아니라,
정해진 규칙을 실행하는 인터페이스로 설계해야 한다.

## 설계 원칙

### 1. 사실과 선호를 분리한다

- `source_text`는 사실 근거다.
- `llm_analysis`는 개선 힌트다.
- `customer_feedback`는 업무 선호와 운영 요구다.

이 세 가지를 섞으면 모델이 무엇을 사실로 봐야 하는지 헷갈린다.

### 2. 프롬프트 책임을 제한한다

프롬프트는 아래만 담당한다.

- 입력 역할 설명
- 우선순위 규칙
- 제외 규칙
- 출력 형식

반대로 아래는 프롬프트 밖에서 관리한다.

- 상담 유형별 필수 항목 사전
- 누적 고객 피드백 룰셋
- 금칙어/민감정보 정책
- 평가 지표와 샘플셋

### 3. 충돌 규칙을 먼저 고정한다

규칙 충돌 시 우선순위는 반드시 고정한다.

1. 정책, 보안, 컴플라이언스
2. 원문에서 직접 확인되는 사실
3. 누적 고객 피드백으로 확정된 업무 규칙
4. LLM 분석 기반 개선 제안
5. 단건 표현 선호

### 4. 프롬프트를 층으로 나눈다

하나의 긴 프롬프트 대신 아래 3개 레이어로 본다.

- 고정 레이어: 항상 유지되는 절대 규칙
- 가변 레이어: 업무 유형별 규칙
- 학습 레이어: 반복 평가와 피드백으로 조정되는 규칙

### 5. 평가 가능한 구조로 설계한다

프롬프트는 잘 써졌는지보다 비교 가능해야 한다.
따라서 초기에 평가 항목도 같이 정의한다.

- 핵심 정보 누락률
- 불필요 정보 포함률
- 고객 피드백 반영률
- 출력 형식 준수율
- 상담 유형별 만족도

## 설계 대상

이 프로젝트에서 먼저 설계해야 할 대상은 아래 순서가 적절하다.

1. 어떤 요약을 좋은 요약으로 볼지 정의
2. 입력 데이터 구조 정의
3. 고정/가변/학습 레이어 분리
4. 충돌 해결 규칙 정의
5. 평가 기준 정의
6. 그 뒤에 실제 프롬프트 문안 작성

## 안티패턴

다음 방식은 피한다.

1. 현업 피드백을 볼 때마다 프롬프트 본문에 문장을 추가하는 방식
2. 모델이 스스로 중요도를 판단하라고만 두는 방식
3. 출력 형식과 판단 규칙을 한 문단에 섞어 쓰는 방식
4. 예외를 모두 프롬프트에 박아 넣는 방식
5. 단건 리뷰를 전체 정책처럼 승격하는 방식

## 권장 방향

실무적으로는 아래 구조가 가장 안정적이다.

- 프롬프트 본문은 짧고 단단하게 유지한다.
- 룰셋은 JSON 또는 테이블로 외부화한다.
- 누적 피드백은 프롬프트가 아니라 별도 정책 데이터로 관리한다.
- LLM 분석 결과는 다음 실행을 위한 개선 입력으로만 사용한다.

즉, 프롬프트 고도화의 목표는 문장을 늘리는 것이 아니라,
프롬프트가 의존하는 구조를 명확히 만드는 것이다.
