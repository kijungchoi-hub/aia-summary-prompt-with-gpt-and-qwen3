# 현업 피드백 예측 가이드

## 목적

현업 피드백을 받은 뒤에 프롬프트 본문에 문장을 추가하는 방식은 금방 한계에 도달한다.
이 문서는 현업이 자주 지적하는 문제를 사전에 예측하고, 이를 구조화된 입력 규칙으로 전환하는 기준을 정의한다.

## 기본 원칙

1. 피드백은 문장으로 누적하지 말고 규칙 유형으로 분류한다.
2. 자주 반복되는 피드백만 `feedback_rules`에 승격한다.
3. 단건 표현 선호는 프롬프트 본문이 아니라 `preferred_labels`로 관리한다.
4. 누락과 과다는 평가 기준과 연결해서 관리한다.
5. 프롬프트 본문은 짧게 유지하고, 책임은 외부 설정으로 분리한다.

## 현업이 자주 주는 피드백 유형

### 1. 누락 피드백

- 고객이 무엇을 요청했는지 안 보인다.
- 처리 상태가 빠졌다.
- 상담사 후속조치가 빠졌다.
- 계약자와 피보험자 관계가 빠졌다.
- 불만 사유나 민원 포인트가 빠졌다.
- 요청 기한 또는 긴급성이 빠졌다.

대응:

- `must_include`
- `priority_topics`
- `analysis_hints.missing_points`

### 2. 과다 피드백

- 인사말, 공감 멘트, 잡담이 너무 많다.
- 배경 설명이 길어서 핵심이 안 보인다.
- 개인정보가 과하게 남아 있다.
- 실무에 의미 없는 세부 금액, 상세 시각이 들어간다.

대응:

- `must_avoid`
- `analysis_hints.over_summary_points`
- `feedback_rules.negative_patterns`

### 3. 순서 피드백

- 고객 요청보다 배경 설명이 먼저 나온다.
- 상태와 후속조치가 섞여 읽기 어렵다.
- 민원 내용이 특이사항에 숨어 있다.

대응:

- `priority_topics`
- `task_config.required_sections`
- 내부 자기검증 체크리스트

### 4. 용어 피드백

- 현업이 쓰는 항목명과 다르다.
- 보고서 용어와 QA 용어가 혼용된다.

대응:

- `preferred_labels`

### 5. 근거성 피드백

- 원문에 없는 해석이 추가된다.
- 고객 감정을 과장한다.
- 처리 결과를 추정해서 쓴다.

대응:

- 고정 레이어 규칙
- `analysis_hints.quality_issues`
- 자체검증 체크리스트

## 예상 현업 피드백 20개

1. 고객 요청 사항이 첫 줄에 안 보인다.
2. 처리 상태가 빠졌다.
3. 상담사 후속조치가 빠졌다.
4. 계약자/피보험자 관계가 빠졌다.
5. 민원 또는 불만 사유가 약하게 표현됐다.
6. 고객이 원하는 최종 결과가 안 보인다.
7. 기한 또는 긴급성이 누락됐다.
8. 완료인지 진행 중인지 모호하다.
9. 배경 설명이 너무 길다.
10. 인사말과 공감 멘트가 남아 있다.
11. 개인정보가 과다하다.
12. 업무 핵심이 아닌 세부 금액이 들어갔다.
13. 업무 핵심이 아닌 상세 시각이 들어갔다.
14. 후속 안내와 현재 상태가 섞여 있다.
15. 고객 발화와 상담사 발화가 뒤섞여 책임 주체가 불명확하다.
16. 원문에 없는 추정 문장이 들어갔다.
17. 감정 해석이 과장됐다.
18. 다른 맥락의 STT가 섞인 것 같다.
19. 항목명이 현업 용어와 다르다.
20. 섹션 순서가 매번 달라 검수가 어렵다.

## 운영 방식

1. 피드백 문장을 받으면 먼저 위 5개 유형 중 어디에 속하는지 분류한다.
2. 3회 이상 반복된 피드백은 `feedback_rules`에 반영한다.
3. 모델 성능 문제로 반복되는 패턴은 `analysis_hints`로 반영한다.
4. 단건 선호 표현은 `preferred_labels`로만 반영한다.
5. 실제 변경 전후는 평가 기준 문서로 비교한다.
